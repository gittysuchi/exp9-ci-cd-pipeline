Description / Theory

CI Continuous Integration

Continuous Integration is a development practice where code changes are automatically built and tested whenever they are pushed to a repository. Bugs are detected within minutes of being introduced, code quality is maintained, and manual testing effort is reduced. Four levels of testing are automated in this experiment:

  • Unit testing validates individual methods (the service layer) in isolation, with the database mocked.
  • Integration testing checks that the REST API works correctly through controller, service and database (MockMvc).
  • Contract testing verifies that the frontend and backend agree on the request / response format (Pact). If the backend changes in a way that would break the frontend, the build fails.
  • Testcontainers start real infrastructure (PostgreSQL) in Docker during the test, making tests more reliable and closer to production.

CD Continuous Deployment

Continuous Deployment is the process of automatically deploying an application after it has passed all tests, so new features reach users quickly and reliably. The application is packaged with Docker, which bundles the app and all its dependencies and removes “works on my machine” problems. GitHub Actions automates the build, test and deployment steps whenever code is pushed.

A canary deployment releases the new version to a small group of users first (10 % here). If the canary behaves well the release is expanded to everyone; if not, it is rolled back automatically — reducing the risk of failures.

Implementation / Procedure

Part A — Continuous Integration

  1. Create a Spring Boot REST service (Product Catalogue) with controller, service and JPA repository layers.
  2. Write unit tests with JUnit 5 and Mockito for the business logic (discount calculation, not-found handling).
  3. Implement API tests using MockMvc — first on the web layer only, then on the full application context.
  4. Define contract tests using Pact: the frontend client records its expectations; the backend verifies them.
  5. Integrate Testcontainers to run repository tests against a real PostgreSQL container.
  6. Configure the CI pipeline (ci.yml) so all tests run automatically on every push and pull request.

Part B — Continuous Deployment

  1. Create a Dockerfile (multi-stage build: Maven build stage, small JRE runtime stage, non-root user, health check).
  2. Build the Docker image and push it to the container registry (GitHub Container Registry; Docker Hub optional).
  3. Configure the GitHub Actions workflow (cd.yml) that starts automatically after CI succeeds.
  4. Automate the build and deployment steps (image build, push, deploy).
  5. Implement the canary deployment strategy: nginx routes 10 % of traffic to the new version; the verification script promotes it to 100 % or rolls it back.
  6. Push the project to GitHub (steps below) — the pipelines now run automatically.

1. Unit test - JUnit 5 + Mockito (ProductServiceTest.java)

/** UNIT TESTS - JUnit 5 + Mockito. The repository is mocked, so no Spring context and no database. */
@ExtendWith(MockitoExtension.class)
@DisplayName("Unit tests - ProductService")
class ProductServiceTest {

    @Mock
    private ProductRepository repository;

    @InjectMocks
    private ProductService service;

    @Test
    @DisplayName("create() saves a product built from the request")
    void createSavesProduct() {
        when(repository.save(any(Product.class))).thenAnswer(inv -> inv.getArgument(0));

        Product saved = service.create(new ProductRequest("Mouse", 799.0, 25));

        assertEquals("Mouse", saved.getName());
        assertEquals(799.0, saved.getPrice());
        assertEquals(25, saved.getStock());
        verify(repository).save(any(Product.class));
    }

    // ...

    @ParameterizedTest(name = "price {0} with {1}% discount -> {2}")
    @CsvSource({
            "1000.0, 10, 900.0",
            "2000.0, 25, 1500.0",
            "499.99, 0, 499.99",
            "100.0, 100, 0.0",
            "333.33, 10, 300.0"
    })
    @DisplayName("priceWithDiscount() applies the percentage and rounds to 2 decimals")
    void discountIsCalculatedCorrectly(double price, double percent, double expected) {
        when(repository.findById(1L)).thenReturn(Optional.of(new Product("Item", price, 1)));

        assertEquals(expected, service.priceWithDiscount(1L, percent), 0.001);
    }

4. Contract test, consumer side - Pact (ProductConsumerPactTest.java)

    @Pact(consumer = "product-frontend")
    public RequestResponsePact getSingleProductPact(PactDslWithProvider builder) {
        return builder
                .given("product with id 1 exists")
                .uponReceiving("a request for product 1")
                .path("/api/products/1")
                .method("GET")
                .willRespondWith()
                .status(200)
                .matchHeader("Content-Type", "application/json.*", "application/json")
                .body(new PactDslJsonBody()
                        .integerType("id", 1)
                        .stringType("name", "Laptop")
                        .numberType("price", 55000.0)
                        .integerType("stock", 10))
                .toPact();
    }

    // ...

    @Test

5. Contract test, provider side - Pact (ProductProviderPactTest.java)

@Provider("product-service")
@PactFolder("src/test/resources/pacts")
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@DisplayName("Contract test (provider) - backend honours the frontend contract")
class ProductProviderPactTest {

    @LocalServerPort
    private int port;

    @Autowired
    private ProductRepository repository;

    @Autowired
    private JdbcTemplate jdbc;

    @BeforeEach
    void setTarget(PactVerificationContext context) {
        context.setTarget(new HttpTestTarget("localhost", port));
    }

    @TestTemplate
    @ExtendWith(PactVerificationSpringProvider.class)
    void verifyPact(PactVerificationContext context) {
        context.verifyInteraction();
    }

    @State("product with id 1 exists")
    void productOneExists() {
        repository.deleteAll();
        jdbc.execute("ALTER TABLE products ALTER COLUMN id RESTART WITH 1");
        repository.save(new Product("Laptop", 55000.0, 10));
    }

    @State("no product with id 999 exists")
    void productNineNineNineMissing() {
        repository.deleteAll();
    }
}

6. CI workflow - triggers and one job (.github/workflows/ci.yml)

# =====================================================================================
#  CONTINUOUS INTEGRATION (CI)
#  Goal   : every push / pull request is automatically built and tested.
#  Answers: "Does the new code compile, and does it still work with the rest of the system?"
#  Stops  : at a verified build artifact (JAR). Deployment is the job of cd.yml.
# =====================================================================================
name: "CI - Build and Test Pipeline"

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]
  workflow_dispatch:

# a newer push cancels the older run of the same branch
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

permissions:
  contents: read

env:
  JAVA_VERSION: "17"

jobs:

# ...

  unit-tests:
    name: "2. Unit Tests (JUnit 5 + Mockito)"
    needs: build
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: ${{ env.JAVA_VERSION }}
          cache: maven

      - name: Run unit tests
        run: mvn -B -ntp -Dtest=ProductServiceTest -Dsurefire.failIfNoSpecifiedTests=false test

      - name: Publish test summary
        if: always()
        run: bash scripts/test-summary.sh "Unit tests (JUnit 5 + Mockito)"

      - name: Upload test reports
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: unit-test-reports
          path: target/surefire-reports/

7. Dockerfile

# ---------- Stage 1: build the JAR ----------
FROM maven:3.9-eclipse-temurin-17 AS build
WORKDIR /workspace
COPY pom.xml .
COPY src ./src
# Tests already ran in the CI pipeline, so the image build skips them
RUN mvn -B -ntp -DskipTests package

# ---------- Stage 2: small runtime image ----------
FROM eclipse-temurin:17-jre-alpine
RUN addgroup -S app && adduser -S app -G app
WORKDIR /app
COPY --from=build /workspace/target/*.jar app.jar

# Release metadata - overridden at deploy time (stable / canary)
ARG APP_VERSION=1.0.0
ENV APP_VERSION=${APP_VERSION} \
    APP_TRACK=stable \
    JAVA_OPTS=""

USER app
EXPOSE 8080

HEALTHCHECK --interval=10s --timeout=3s --start-period=40s --retries=6 \
  CMD wget -qO- http://localhost:8080/actuator/health | grep -q UP || exit 1

ENTRYPOINT ["sh", "-c", "exec java $JAVA_OPTS -jar app.jar"]

8. CD workflow - triggers and canary job (.github/workflows/cd.yml)

# =====================================================================================
#  CONTINUOUS DEPLOYMENT (CD)
#  Goal   : a change that PASSED CI is automatically packaged, released and rolled out.
#  Answers: "Can we safely put this verified build in front of real users?"
#  Starts : automatically after the CI workflow succeeds on main (or manually).
#  Strategy: CANARY - 10 % of traffic first, verify, then 100 %; automatic rollback on failure.
# =====================================================================================
name: "CD - Docker Build, Push and Canary Release"

on:
  workflow_run:
    workflows: [ "CI - Build and Test Pipeline" ]
    types: [ completed ]
    branches: [ main ]
  workflow_dispatch:
    inputs:
      simulate_canary_failure:
        description: "Make the canary fail on purpose (demonstrates automatic rollback)"
        type: boolean
        default: false

concurrency:
  group: cd-release
  cancel-in-progress: false

permissions:
  contents: read
  packages: write        # push images to GitHub Container Registry (ghcr.io)

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: exp9-cicd-demo

jobs:

# ...

  canary-deploy:
    name: "2. Canary Deploy (10 percent traffic) and Verify"
    needs: build-and-push
    runs-on: ubuntu-latest
    timeout-minutes: 20
    env:
      NEW_IMAGE: ${{ needs.build-and-push.outputs.image }}:${{ needs.build-and-push.outputs.tag }}
      STABLE_TAG_IMAGE: ${{ needs.build-and-push.outputs.image }}:stable
      VERSION: ${{ needs.build-and-push.outputs.version }}
    steps:
      - name: Checkout deployment files
        uses: actions/checkout@v4
        with:
          ref: ${{ github.event.workflow_run.head_sha || github.sha }}

      - name: Log in to GitHub Container Registry
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Resolve the stable (previous) release
        run: |
          docker pull "$NEW_IMAGE"
          if docker pull "$STABLE_TAG_IMAGE" > /dev/null 2>&1; then
            echo "Previous stable release found: $STABLE_TAG_IMAGE"
            echo "STABLE_IMAGE=$STABLE_TAG_IMAGE" >> "$GITHUB_ENV"
          else
            echo "First release ever - using the new image as the stable baseline"
            echo "STABLE_IMAGE=$NEW_IMAGE" >> "$GITHUB_ENV"
          fi
          echo "CANARY_IMAGE=$NEW_IMAGE" >> "$GITHUB_ENV"

      - name: Deploy canary (stable 90 percent / canary 10 percent)
        run: bash deploy/canary-deploy.sh "$STABLE_IMAGE" "$CANARY_IMAGE" "$VERSION" "${{ inputs.simulate_canary_failure || 'false' }}"

      - name: Verify canary health with live traffic
        run: bash deploy/verify-canary.sh 50

      - name: Show container logs when verification failed
        if: failure()
        run: docker compose -f deploy/docker-compose.canary.yml logs --tail=40 canary || true

      - name: Tear down canary environment
        if: always()
        run: docker compose -f deploy/docker-compose.canary.yml down --remove-orphans || true

9. Canary traffic split - nginx (deploy/nginx/canary.conf)

# CANARY: weighted round-robin  ->  9 of every 10 requests go to stable, 1 of 10 to canary (10 %)
upstream app {
    server stable:8080 weight=9;
    server canary:8080 weight=1;
}

server {
    listen 80;

    location / {
        proxy_pass http://app;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}

  2. In VS Code: File → Open Folder → select the extracted exp9-ci-cd-pipeline folder. Open the terminal with Ctrl + `.
  3. Tell Git who you are (one time only):
git config --global user.name  "Your Name"

git init -b main
git add .
git commit -m "Experiment 9: CI/CD pipeline"
git remote add origin https://github.com/<your-username>/exp9-ci-cd-pipeline.git
git push -u origin main

A browser window opens the first time so you can sign in to GitHub (Git Credential Manager). If asked for a password in the terminal, use a Personal Access Token, not your account password.

One-command alternative: .\scripts\push-to-github.ps1 -RepoUrl https://github.com/<your-username>/exp9-ci-cd-pipeline.git (PowerShell) or bash scripts/push-to-github.sh <repo-url> does init, add, commit, remote and push for you.
  1. Automatic posting: run git config core.hooksPath .githooks once. From then on every git commit is pushed to GitHub automatically by the post-commit hook, which immediately starts the CI pipeline.
  2. Open the repository on GitHub → Actions tab. The CI - Build and Test Pipeline workflow starts; when it succeeds the CD - Docker Build, Push and Canary Release workflow starts by itself.
  3. To demonstrate the rollback: Actions → CD → Run workflow → tick simulate_canary_failure → the canary fails and the Rollback job runs.

On every push the code is automatically built and tested at four levels (unit, integration, contract, Testcontainers); once CI passes, the application is packaged as a Docker image, pushed to a container registry and released with a canary strategy that either promotes the release to all users or rolls it back automatically.
